# Backend Implementation Principles & Patterns

This document defines the architectural patterns, coding standards, and best practices for the **CAR2Hand** backend. We prioritize **Clean Code**, **Type Safety**, and **Maintainability** using the ElysiaJS + Prisma + Bun stack.

---

## 1. Core Principles (Clean Code)

- **Single Responsibility Principle (SRP)**: Each function, service, or route should do only one thing.
- **Meaningful Naming**: Use descriptive names for variables, functions, and classes. Avoid abbreviations (e.g., `userRepository` instead of `uRepo`).
- **Small Functions**: Keep functions short and focused. If a function is too long, extract logic into smaller helper functions.
- **Fail Fast**: Validate inputs early using Zod schemas and return errors immediately.
- **Don't Repeat Yourself (DRY)**: Abstract common database queries or business logic into shared services or utilities.

---

## 2. Layered Architecture

We use a layered approach to separate concerns and make testing/maintenance easier:

### A. Routes Layer (`src/*.ts`)
- **Responsibility**: Handle HTTP requests, validate input (Zod), and call the Service layer.
- **Rule**: No direct business logic or complex database queries here.
- **Elysia Example**:
  ```typescript
  .post('/login', async ({ body, set }) => {
    const result = await AuthService.login(body);
    return result;
  }, { body: LoginSchema })
  ```

### B. Service Layer (`src/services/*.ts`)
- **Responsibility**: Contain business logic, orchestrate multiple database calls, and handle complex rules.
- **Rule**: This layer is the "source of truth" for business rules.
- **Pattern**: Exported classes or objects with static methods.

### C. Database Layer (`prisma/schema.prisma` & `src/db.ts`)
- **Responsibility**: Manage data persistence and schema definitions.
- **Rule**: Use Prisma for all database interactions. Keep the schema organized with clear relations and indices.

---

## 3. Data Validation & Type Safety

- **Input Validation**: Use **Zod** (via Elysia's `t.Object` or external schemas) for every endpoint.
- **Strict Types**: Leverage the types generated by Prisma (`Admin`, `User`, `VehicleListing`).
- **Standardized Responses**: Use a consistent response format for success and error cases.

---

## 4. Error Handling

- **Custom Exceptions**: Define clear error types (e.g., `NotFoundError`, `UnauthorizedError`).
- **Standard HTTP Codes**:
  - `200/201`: Success
  - `400`: Bad Request (Validation failure)
  - `401/403`: Authentication/Authorization issues
  - `404`: Resource not found
  - `500`: Unexpected server error

---

## 5. Security Best Practices

- **JWT Authentication**: Use the `jwt` plugin from Elysia. Never store sensitive data (like passwords) in tokens.
- **Password Hashing**: Use `Bun.password` or a standard library like `bcrypt`.
- **CORS**: Strictly define allowed origins in production.
- **Environment Variables**: Never commit `.env` files. Use `.env.example` as a template.

---

## 6. Maintenance & Scalability

- **Database Indices**: Ensure foreign keys and frequently searched columns are indexed in `schema.prisma`.
- **Logging**: Log significant events (errors, auth failures, critical mutations) to help with debugging.
- **Documentation**: Use JSDoc for complex logic and maintain a clear API structure.
